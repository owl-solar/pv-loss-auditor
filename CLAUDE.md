# PV Loss Auditor

Portfolio project for Solar Performance / Asset Performance Engineer roles.
Diagnoses underperformance of a PV plant: compares actual generation with
weather-corrected expected generation, computes plant KPIs and breaks losses
down by cause into a loss waterfall in kWh and EUR.

This is project 1 of a chain:
1. **PV Loss Auditor** (this repo) – find losses
2. Repowering Planner – decide what to do (NPV / IRR / LCOE of scenarios), uses outputs of this repo
3. O&M Copilot – RAG assistant for alarm codes and manuals

## Data
- **NREL PVDAQ** via OEDI public S3 bucket (`oedi-data-lake/pvdaq`) + its metadata file.
  Selection criteria: ≥3 years of data, POA irradiance, module temperature, AC power,
  known tilt/azimuth/DC & AC capacity; inverter-level data preferred.
- **Open-Meteo** historical weather as a reanalysis alternative to on-site sensors: ERA5 and ECMWF IFS
  (archive API, always with explicit `models=`). The satellite API has **no coverage at 9069**; nothing
  in the project is satellite data. A true satellite source would be NSRDB (free key) or NASA POWER.
- **Electricity prices**: US market prices matching the plant's location and connection type:
  ISO day-ahead LMP (via `gridstatus`) for grid-connected plants in an ISO;
  utility/state commercial tariff (EIA) for behind-the-meter systems;
  regional wholesale estimate (EIA) for plants outside ISO regions.
  Losses reported in USD (optional EUR conversion). Document the price assumption explicitly.
  **9069 price (decided):** utility-scale, front-of-meter (step-up transformers and a nearby
  high-voltage substation on satellite images; inverters / meter 2 = 1.02), in Georgia, which has
  no ISO / RTO and no EIA wholesale hub. Flat **30.19 USD/MWh** = Georgia Power avoided energy
  cost 2026, "Solar Ground-Mounted Fixed Tilt", from the 2025 projections filed with the Georgia
  PSC (filing #223157, dockets 4822 / 16573; file in `data/raw/prices/`; `src/pv_loss_auditor/prices.py`;
  `price:` in the config). Report a band of ±30 % (21.13 … 39.25). Always state: it is a
  projection applied to 2020–2023 (realised 2021–22 wholesale was higher), the utility's avoided
  cost and not this plant's PPA price (unknown). The ranking of loss causes in kWh does not depend
  on the price. Repowering Planner can reuse the 2026–2045 curve of the same file.
- Never invent or "fill in" real measurements. Anything synthetic (e.g. injected string faults) must be generated by an explicit, documented script and labelled as synthetic everywhere.

## Expected yield and KPIs of 9069 (Phase 2 done)
`notebooks/02_expected_yield.ipynb`, `src/pv_loss_auditor/model.py`, `src/pv_loss_auditor/kpi.py`, `src/pv_loss_auditor/sensor_checks.py`,
parameters in `model:` / `kpi:` of the config. Decisions (taken by me under "use best practice"):
- POA = mean of cells 04 / 10; T_cell = mean thermocouple 01 / 06 s1 / 10 + 3 °C × G/1000;
  no modelled fallback (measured T on 97.7 % of daylight steps; Faiman default reads +5.8 °C).
- Model: pvlib `pvwatts_dc` (967.2 kW per inverter, γ = DC-weighted nameplate −0.416 %/°C) ×
  (1 − 6.34 % design DC losses: LID 1.5, mismatch 2, wiring 1.5, connections 0.5, nameplate 1)
  → `pvlib.inverter.pvwatts` (η_nom 0.98), clipped at 825 kW. Not calibrated on the data.
- PR at inverter-step level, ratio of sums; variants A raw / B T_ref 25 °C / C T_ref 41.5 °C
  (POA-weighted mean T_cell of the period), each with and without downtime, plus meter PR (C).
  C for trends and the waterfall, B for STC / contract comparisons. B and C remove the seasonal
  swing of A (monthly std 0.034 → 0.019 / 0.018). PR (C) of running inverters 0.762 (2020–2022),
  0.735 (2023); annual PR (C) changes ≤ 0.002 between γ −0.28 and −0.416.
- Availability time-based: down = AC < 1 % of rating at POA > 50 W/m²; unknown AC leaves the
  denominator. 0.957 / 0.966 / 0.830 / 0.692 (2020–2023). **Revised in Phase 5** (notebook 02,
  last section; `losses.availability_revised`): energy-based, net of channel loss 0.967 / 0.971 /
  0.838 / **0.791**, upper bound 0.977 / 0.978 / 0.845 / 0.939; quote 2023 as 0.79 (raw 0.69 is a
  lower bound). From 2023-03 every day is a channel-loss day, so the upper bound is 1.00 there.
  PR (C) with downtime: use the meter PR 0.717 / 0.727 / 0.622 / 0.581 (inverter-based
  0.733 / 0.737 / 0.636 / 0.514 is understated by ~7 pp in 2023).
- Closed: AC lead of ~7 min is curve shape (temperature), not a clock error (morning −14 min,
  afternoon 0 min; after temperature correction both within ±2 min); no time shift applied.
  Measured γ −0.34 ± 0.04 %/°C per inverter (flattened by regression dilution), no inverter group
  at −0.28; inverters 29–40 slightly flatter (−0.30 vs −0.35), not conclusive.

## Degradation, soiling and external weather of 9069 (Phase 4 done)
`notebooks/04_degradation_soiling.ipynb`, `src/pv_loss_auditor/degradation.py`, `src/pv_loss_auditor/openmeteo.py`,
`degradation:` in the config; Open-Meteo cache in `data/raw/openmeteo/` (0.9 MB, not committed).
Decisions (taken with me, options first): RdTools fed with both normalized energy (measured /
PVWatts expected) and PR (C), running inverters only; shortfall split by per-factor estimates plus
an unexplained remainder shown as a range; ERA5 + IFS; AOI = ASHRAE b0 0.05.
- Day filters (my assumptions): ≥ 90 % usable inverter-steps, ≥ 50 % of them running, ≥ 2 kWh/m² POA
  → 1093 of 1309 days. Normalized energy median 0.902 / 0.890 / 0.895 / 0.865 (2020–2023).
- Degradation (YoY): before 2023 −0.5 … −1.3 %/yr depending on the filters (RdTools CI ±0.3 does not
  include that choice); with 2023 −1.6 … −2.0 %/yr = a step, not ageing. State "about −1 %/yr ±
  0.5 before 2023", never a single decimal. The two series agree within 0.1 pp.
- Soiling (SRR): 1.4 % with ERA5 rain ≥ 2 mm as cleaning (1.1–1.6 % for 1–5 mm); 2.7 % without rain
  data is an overestimate (noise taken as cleanings). Only 10 of 27 intervals valid. Same value
  before 2023, so soiling does not explain the 2023 step.
- External weather vs cells 04 / 10: POA +1.6 % (ERA5) / +2.0 % (IFS) at > 200 W/m², hourly nRMSE
  22 %, monthly +3…6 %; raw PR from Open-Meteo 2–6 pp below the cells. 12-month ratio ERA5 / cells
  flat (1.058 → 1.056): no cell drift, 2023 step not a sensor effect. IFS rises (→ 1.089), probably
  ECMWF model versions (hypothesis). Winter ratio +10…+19 %, summer −4…+4 %: cause not separable.
- AOI ≤ 3.0 % of POA (1.8–4.1 for b0 0.03–0.07), flat over seasons and years; upper bound because
  the reference cells also lose to reflection.
- Unexplained shortfall (% of expected): 5.4–9.6 (2020–22), 9.2–12.2 (2023). Open-Meteo hourly
  data are means of the PRECEDING hour (labels at hour end).

## Loss waterfall of 9069 (Phase 3 done, MVP not yet published)
`notebooks/03_loss_waterfall.ipynb`, `src/pv_loss_auditor/losses.py`, `tests/` (`python -m pytest`, 178 tests after the production refactor), `losses:` in the config. Decisions (taken with me, options first):
- Sequential cascade in physical order: nominal (P0·G/1000) → temperature (γ nameplate, T_ref
  25 °C) → design DC losses → inverter efficiency → clipping (= expected) → downtime → AC unknown
  → channel credit → running shortfall → meter reconciliation → after inverters (= meter 2).
  Ends at the meter (revenue basis); closure checked by `check_closure`. Scope: daylight steps
  with POA, T_cell and meter known (95.7–99.2 % of daylight steps per year).
- Downtime vs channel loss: a local day with sum(inverters) / (meter × 1.022) < 0.97 is a
  channel-loss day; the meter surplus is credited back (negative step). It cannot say which
  inverter lies; 1 pp of the factor 1.022 moves the 2023 credit by ≈ 0.35 GWh.
- Results 2020-05…2023-11: design 35.9 GWh, downtime net of channel loss 23.4 GWh (0.71 M USD),
  running shortfall 19.9 GWh (0.60 M USD), after inverters 3.4 GWh; downtime + shortfall = 1.31 M
  USD (0.91…1.70 M) at 30.19 USD/MWh ±30 %. Downtime: 3 / 3 / 14 / 26 % of nominal 2020–2023;
  2023 channel loss 4.8 GWh. Clipping ≤ 0.08 % (upper bound); no curtailment plateau (97 % of
  plateau steps already stale; the "0.19 shelf" is weak light); AC above rating 0.65 MWh, left as
  measured. Swapping temperature / DC order moves 0.4–0.5 % of nominal.
- The 6.34 % design DC losses are an assumption (no PVsyst report): 4 / 8 % moves the running
  shortfall to 24.2 / 16.8 GWh, downtime stays within 0.7 GWh.

## Anomalies and outages of 9069 (Phase 5 done)
`notebooks/05_anomaly_detection.ipynb`, `src/pv_loss_auditor/anomalies.py`, `src/pv_loss_auditor/synthetic_faults.py`,
`src/pv_loss_auditor/outages.py`, `anomalies:` in the config. Decisions (taken with me, options first):
- Residual = measured / expected AC per inverter, divided by the median of the running inverters
  at the same step (removes season, weather, soiling, the 2021 and 2023 steps; steps with POA >
  200 W/m², model < 90 % of rating, ≥ 10 peers). Healthy inverters sit at fixed offsets 0.96 …
  1.05 from their peers, so features are deviations from the inverter's own 121-day norm.
- Detectors: Isolation Forest (4 and 2 features) and a plain rule (daily median below k robust
  sigmas, sigma from the REAL data: from the injected table it is inflated). Threshold chosen on
  2020–2021, reported on 2022–2023; **main criterion = false-alarm budget ≤ 1 % of clean
  inverter-days** (max F1 picked the grid edge for all three detectors, forests 0.12 = max, rule
  k = 1 = min, and gave 7–18 % false alarms; corrected in Phase 6, earlier notes said "twice"). Event detected
  = ≥ 3 flagged days.
- SYNTHETIC string faults (config `anomalies.synthetic`, seed 9069): k = 1, 2, 3, 5, 10, 20, 40
  strings of 170 per inverter (170 is derived: 967 kW / (19 × 0.300 kW); metadata string counts
  are wrong), 21 and 60 days, abrupt, constant, applied to AC; 168 events, 62 in the test years.
  Real events (inv30 2020-09-22…11-04, inv13 2021-11-19…12-15, plant-wide stops) are excluded.
- Results (test years, 1 % budget): rule finds 50 % of events at precision 0.91, forest 16–18 %
  at 0.57–0.59. **Practical detection limit about 10 strings (≈ 6 % of an inverter)**; of 30
  events with 1–5 strings only 2 found. The idea that noisy features dilute the forest is NOT
  supported (2 features no better). Real inv30: rule 38 of 41 days, forests 1–3; inv13: all 7 of 7.
- Found in Phase 6 (dashboard): inv30 over-performs by +0.09 … +0.16 against its own norm from
  2020-08-21 to 2020-09-21, right before the labelled real event (config window starts 09-22).
  The forest flags 20 days there and only 1 inside the event; the rule 20 days outside, scattered
  over 2020-07 … 2021-01. Those days are labelled clean, so they count as false alarms: 20 days =
  0.1 % of the 16 896 clean inverter-days of the tuning years, against a budget of 1 %. Cause
  unknown; the own-norm window is an unlikely reason (≤ 37 % of its 121 days lie in the event).
  Decision: window kept as is (see "Where we stopped", sensitivity in the README).
- Limits to state with any number: faults are synthetic, abrupt and AC-side; 62 test events in
  14 cells (1–7 each); precision depends on the share of injected days (17 % of all
  inverter-days, 12 % in the test years); own norm absorbs slow drift
  and faults longer than ~60 days (the 61-day window missed the real 45-day inv30 event); the
  5-minute localisation level was not built; the 2023 step is plant-wide and cannot appear in a
  peer-normalised residual.
- Outages (`src/pv_loss_auditor/outages.py`): stops are real (meter agrees, sum/meter ≈ 1.00) in 2021-10…12 and
  2022-05-23…12-10 (inverters 23, 24, 35–40 for 149 days); in 2021-01 and 2022-12…2023-11 the
  ratio is 0.80–0.91 with 8–14 inverters "stopped": a substantial share are lost channels.
  A fault of a single string is below the noise (1 string = 0.59 %, robust noise 0.68 %).

## Engineering rules (from this work, apply to every change)
- **Every new function in `src/pv_loss_auditor/` comes with a test in `tests/`**, and physics tests state the
  answer worked out by hand, not copied from the program's output.
- **Before each commit: `ruff check .`, `ruff format .`, `mypy` and `pytest`** (pre-commit does the first two).
- **`golden_values.json` changes only on purpose**, with the reason in the commit message. A difference after a
  refactor is a bug to find, never a reason to update the file. Check: `python -m scripts.compare_golden --run fixture`
  (and `--run full` locally when the calculation code was touched).
- **Never re-download data; CI runs on fixtures only** (no PVDAQ, Open-Meteo or price download in tests or CI).
  Tests must not need `data/raw` or `data/processed`: use the fixture or synthetic data labelled SYNTHETIC.
- Invalid inputs raise `ValueError` with the argument name (use `validation.py`); suspicious but usable data
  gives `log.warning`. No `print` in the package: use `logging.getLogger(__name__)`; handlers only in `main()`.
- Randomness always seeded (`random_state` / `default_rng` from the config).
- Check the clean state of CI-relevant changes with a fresh `git clone` of the repo (no data folders) before pushing.
